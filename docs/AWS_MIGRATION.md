# Migration seam: Supabase today, AWS Amplify later

The backend is **not** migrated now. This document describes the seam that makes a later migration a
data-layer change, not an app rewrite, and what will change when it happens.

## 1. The seam

```
Screens (Home, Add, Details) ──► EquipmentRepository (interface) ◄── RepositoryProvider (App.tsx)
        no backend imports                  │
                                            ├── supabaseEquipmentRepository   (today, live)
                                            ├── mockEquipmentRepository       (tests, no backend)
                                            └── amplifyEquipmentRepository    (future, not built)
```

| Rule | How it is enforced |
|---|---|
| UI depends only on `EquipmentRepository`, `RepositoryContext` and `DataError` | ESLint `no-restricted-imports` on `src/screens`, `src/ui`, `src/navigation`, `src/domain` and `App.tsx`: bans `@supabase/*`, `aws-amplify`, `@aws-amplify/*`, `@aws-sdk/*`, `src/data/supabase*`, `src/data/amplify*`, `src/config/env` |
| The rule itself works | `__tests__/architecture.test.js` lints sample bad imports and expects rejection |
| No Supabase types in UI | Screens use only domain types (`Equipment`, `NewEquipment`) and `DataError`; the data-source badge reads `DATA_SOURCE_LABELS` |
| Every adapter behaves the same | `__tests__/repositoryContract.test.ts` runs one contract suite against every adapter |

Only two places know which backend exists: `src/data/index.ts` (`createDefaultRepository()`) and
`src/config/env.ts` (build-time configuration).

## 2. The adapter contract (what an Amplify adapter must implement)

`src/data/EquipmentRepository.ts`:

```ts
type DataSourceName = 'supabase' | 'mock' | 'amplify';

interface EquipmentRepository {
  readonly source: DataSourceName;            // 'amplify'
  list(): Promise<Equipment[]>;               // ≤ 50 records, newest first
  create(input: NewEquipment): Promise<Equipment>;
}
type Equipment    = { id: number; name: string; price_per_hour: number };
type NewEquipment = { name: string; price_per_hour: number };
```

| Requirement | Detail |
|---|---|
| `list()` | At most 50 records, **newest first**; malformed rows skipped (use `isValidEquipment` / `toEquipment`); numbers are numbers |
| `create()` | Input is already validated; send only `name` and `price_per_hour`; resolve with the stored record including its id, which `list()` then returns first |
| Errors | Reject **only** with `DataError` (`network`, `timeout`, `permission`, `not_found`, `rejected`, `unknown`); never expose backend messages, keys or submitted values |
| Timeouts | Requests time out (≈10 s) with `DataError('timeout')` instead of hanging |
| Identity | `source = 'amplify'`, so the UI shows **"Live data · AWS"** |
| Proof | Add the adapter to `ADAPTERS` in `__tests__/repositoryContract.test.ts`; it must pass unchanged |

Suggested shape, mirroring the Supabase adapter (factory receives an injectable client, so tests need no AWS):

```ts
// src/data/amplifyEquipmentRepository.ts  (future)
export function createAmplifyEquipmentRepository(client: AmplifyDataClient, options?: { timeoutMs?: number }): EquipmentRepository
```

**IDs:** Amplify Data models use string IDs by default. Either define `equipmentId: Int` with a sequence
the app relies on, or (the cleaner option) widen `Equipment.id` to `string` across the domain in a separate,
tested change before the migration. Ordering "newest first" must then use `createdAt`.

## 3. What changes during migration

| Concern | Supabase (today) | AWS Amplify (future) |
|---|---|---|
| **Data API** | PostgREST over HTTPS: `from('equipment').select().order().limit()` / `.insert()` | Amplify Data (AppSync GraphQL): `client.models.Equipment.list()` / `.create()` via `generateClient()` from `aws-amplify/data` |
| **Schema** | `supabase/schema.sql` (Postgres table, check constraints) | `amplify/data/resource.ts` model (`a.model({ name: a.string().required(), pricePerHour: a.float().required() })`) plus validation (custom resolver or Lambda) to keep the 2–60 char / 0–100000 rules |
| **Field names** | `price_per_hour` | Likely `pricePerHour`; the adapter maps to the domain's `price_per_hour`, and the UI is unaffected |
| **API configuration** | `SUPABASE_URL` + `SUPABASE_PUBLISHABLE_KEY`, inlined by Babel at build time | `amplify_outputs.json` (endpoint, region, auth config) generated by `ampx` per environment, loaded with `Amplify.configure(outputs)`. Contains no secrets, but is still build-time configuration: one binary per backend unless loaded at runtime |
| **Authorization** | Row-level security: anon may `select` and `insert`; no update/delete | Model authorization rules, e.g. `allow.guest().to(['read', 'create'])` (Cognito identity pool, unauthenticated role), or `allow.authenticated()` once sign-in exists. No update/delete rules = denied |
| **Authentication** | None (anonymous publishable key) | Cognito Identity Pool guest credentials (or API key for a pure demo); later Cognito User Pool sign-in. Adapter itself is unchanged; `Amplify.configure` + auth mode change |
| **Errors** | PostgREST codes (`42501`, `23514`, `PGRST205`…) → `DataError` in `mapBackendError` | GraphQL `errors[]` / `errorType` (`Unauthorized`, `ConditionalCheckFailedException`, network `TypeError`) → same `DataError` kinds in an Amplify `mapBackendError` |
| **Timeouts** | `AbortController` + `abortSignal()` | Amplify request cancellation (`client.cancel(promise)`) or a `Promise.race` timeout |
| **CI checks** | SIT/PRE-PROD/PROD run `__integration__` against Supabase using environment secrets | Same stages; integration tests target the Amplify sandbox/branch backend. CI deploys with OIDC → IAM role (see docs/SECRETS.md), never stored keys |
| **Secrets in the app** | Publishable key only | None (the outputs file is public configuration). Server credentials never enter the bundle (`babel.config.js` allow-list test) |

## 4. Migration plan (when the time comes)

1. Create the Amplify backend (`npx ampx sandbox`) with the `Equipment` model and guest read/create authorization.
2. Decide the ID strategy (section 2) and land it as its own tested change.
3. Implement `createAmplifyEquipmentRepository` + error mapping; add it to the contract test `ADAPTERS`.
4. Select it in `createDefaultRepository()` when Amplify configuration is present.
5. Add Amplify integration tests to SIT/PRE-PROD/PROD with OIDC-based AWS access.
6. Migrate data (export `equipment` from Supabase, import into DynamoDB) and run both backends in SIT.
7. Release as a new version through the same gates; Supabase stays available for rollback until PROD is proven.

Nothing in the screens, navigation, validation or tests of UI behaviour needs to change.
